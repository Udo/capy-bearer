:sig
function component(name : string) string
function component(name : string, props : as dval) string

:params
name : a component path, optionally followed by `:HANDLER`
props : optional input, readable inside the component as `request.props`

:returns
The component output as a string.

:content
`component()` renders a component and returns everything it printed as a string.

It collects the output into a buffer, which costs something. Reach for `component_render()` instead when you are writing the fragment straight into the current response and never look at the string — it skips the buffer entirely, so `component_render("card")` does less work than `print(component("card"))`.

Capture the string when the string is the goal: wrapping the fragment in surrounding markup, checking whether it produced anything before emitting a container, storing it in a `dval` beside other values, or emitting the same fragment more than once from one call.

## How a name resolves

A name is a path with an optional `:HANDLER` suffix. Bearer appends `.capy` when the path has no suffix, so `"card"` and `"card.capy"` mean the same file.

A path that starts with `/` is tried first as a real filesystem path and then as a site-root path, so `"/tests/capy-request-context.capy"` means that file under the site root.

A relative path is tried against three directories, in order:

1. the directory of the entry unit that is handling the request
2. the directory of the unit calling `component()`, when that differs
3. the site root

The first match wins. A resolved path that escapes the site root is rejected. Use `component_resolve()` to see which file a name reached, and `component_exists()` to test a name before rendering it.

## Named handlers

`"lib/widgets.capy:CARD"` calls the `COMPONENT:CARD` handler in that file. A name that is only `":CARD"` calls `COMPONENT:CARD` in the file that is currently rendering, which lets one file hold several related fragments.

A file with no named handler must define a plain `COMPONENT` handler.

## What the component sees

`props` arrives as `request.props`. It is swapped in for the duration of the call and restored when the component returns, so a component cannot disturb its caller's props, and nested components each read their own.

Relative paths inside the component resolve against the component's own file, not the caller's — a component in `lib/` can call `component("sibling")` and reach `lib/sibling.capy`.

The target unit's `ONCE` handler runs before the component handler the first time that unit is used in the request.

:errors
An unresolvable component does not raise an error. Bearer sets the response status to `500`, returns a banner element describing the failure in place of the component output, and continues rendering the rest of the page. Guard optional components with `component_exists()` when a missing file should not be an error.

:example capy render
print(component("/doc/examples/card.capy:CARD", {title: "Release notes"}), "\n")

:example capy render wrap the captured output
var body := component("/doc/examples/card.capy:CARD", {title: "Ada"})
print("<section>", body, "</section>", "\n")

:example capy render render a list of components
var titles := ["Ada", "Grace"]
for title := titles {
    print(component("/doc/examples/card.capy:CARD", {title: title}))
}
print("\n")

:example capy render skip a component that may not exist
if component_exists("/doc/examples/card.capy") {
    print(component("/doc/examples/card.capy:CARD", {title: "Optional"}), "\n")
} else {
    print("no card component\n")
}
