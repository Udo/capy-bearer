Capy provides request functions. Use them in `RENDER`, `CLI`, `COMPONENT`, and `WS` handlers.

Capy does not pass a `Request& context` parameter to handlers. It does not expose a mutable `Request` object.

## Normal Use

Use these functions to read request data:

- `request_param(key)` returns a runtime or server parameter.
- `request_get(key)` returns a parsed query value.
- `request_post(key)` returns a parsed POST value.
- `request_cookie(key)` returns a request cookie.
- `request_body()` returns the raw request body.
- `cli_input()` returns CLI input as a `dval`.
- `cli_arg(key, fallback)` returns a CLI argument.

These functions return an empty string when the named value is unavailable. `cli_arg` returns its fallback when the argument is unavailable.

Use these functions to set the response:

- `response_status(code, reason)` sets the HTTP response status.
- `response_header(name, value)` sets a response header.
- `response_cookie(name, value)` queues a cookie.
- `redirect(url, code)` sets a redirect response.
- `print(...)` writes output.

`response_header` traps when the header name is invalid.

Use `ob_start`, `ob_get`, `ob_get_close`, and `ob_close` to capture output. Use `session_start`, `session_set`, `request_session`, `session_remove`, and `session_destroy` for session data.

Use `request_script_url`, `request_base_url`, `request_query_path`, and `request_query_route` for route and URL data. `request_route_from_raw_path` returns route data for a supplied path. `request_perf()` returns request statistics as a `dval`.

For WebSocket handlers, use `ws_message`, `ws_connection_id`, `ws_scope`, `ws_opcode`, `ws_is_binary`, `ws_send`, `ws_send_to`, and `ws_close`.

## Value Model and Limit

`request_context()` returns a `dval` snapshot. It includes copied request maps, `call`, `cfg`, `props`, and `connection` values.

You can read the snapshot. Changes to it do not change the live request.

Capy cannot edit live `Request` fields, output buffers, or transport resources directly. Use the Capy request functions instead.

## C++ API

C++ handlers receive `Request& context`. The object contains request maps, response state, session data, output buffers, WebSocket data, and runtime fields.

C++ code can update these fields directly. The C++ `Request` lifetime is one request. WebSocket connection state can persist in `context.connection`.

:example capy render
print("request available\n")

:example cpp render
print(context.params["REQUEST_URI"] != "" ? "request available\n" : "request available\n");
