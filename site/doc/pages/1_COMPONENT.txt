:title
COMPONENT

:sig
COMPONENT(Request& context)

:see
>component

:content
`function COMPONENT` defines the default Capy component entrypoint.

Use `function COMPONENT { ... }` for the normal form. Use `function COMPONENT:NAME { ... }` for a named component. Each form can instead accept one `request : request` value. The value is opaque and has no C++ object layout.

A component handler accepts zero inputs or one `request` input. It returns no value. Component props cross the Bearer boundary as a copied `dval` value. Use `request_context()` or `request_context(request)` to read that snapshot.

Call `component()` to capture component output as a string. Call `component_render()` to write component output. The helpers call `COMPONENT` by default. A `:NAME` target selects `COMPONENT:NAME`. A target that starts with `:NAME` resolves in the current unit.

Use `COMPONENT` in a reusable unit. A unit can define `COMPONENT` without `RENDER`. `ONCE` runs before the first component call for that unit and request. `INIT` runs when a worker loads the unit.

The compiler rejects other parameter forms, a return type, handler overloads, and `COMPONENT_NAME` syntax. A trap in the handler stops that component invocation.

## C++ API

C++ declares `COMPONENT(Request& context)` or `COMPONENT:NAME(Request& context)`. C++ reads live component props from `context.props` and passes the live context to component helpers.

Capy does not expose C++ `Request&`, `context.props`, or mutable `DValue` aliases. It uses an opaque request handle and copied `dval` snapshots.
