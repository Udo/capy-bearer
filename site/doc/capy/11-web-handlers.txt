## Handler forms

A Bearer unit can declare these Capy handlers:

- `CLI` handles command-line execution.
- `RENDER` handles a normal page request.
- `COMPONENT` renders reusable content.
- `WS` handles a WebSocket message.
- `SERVE_HTTP` handles a request for a server started through Bearer.
- `TASK` handles durable queued work.
- `ONCE` and `INIT` expose Bearer's lifecycle entry points.

`RENDER:NAME`, `COMPONENT:NAME`, `SERVE_HTTP:NAME`, and `TASK:NAME` declare named handlers. A handler cannot be overloaded, generic, variadic, coercive, or return a value. A non-task handler accepts no parameter or one `request` parameter. Every task handler requires exactly one `request` parameter.

`ONCE` and `INIT` exports exist for ABI parity, but their automatic ordering and deduplication contract is not defined yet. Do not rely on them for application lifecycle behavior.

## Rendering a response

A `RENDER` function handles a normal page request:

```capy
function RENDER {
    var name := first(request_get("name"), "world")
    print(<><h1>Hello, <?= name ?></h1></>)
}
```

Use these request functions for common values:

- `request_get(name)` reads a query parameter.
- `request_post(name)` reads a form value.
- `request_cookie(name)` reads a cookie.
- `request_session(name)` reads a session value.
- `request_param(name)` reads a server or request parameter.
- `request_body()` returns the raw request body.

Each function returns a string. It returns an empty string when the key is absent. Use `request_context()` when you need the copied structured request map or component properties. The snapshot includes request data, application config, connection data, input, and the current unit, but not Bearer's operational server configuration.

## Status, headers, cookies, and redirects

```capy
function RENDER {
    response_status(201)
    response_header("Content-Type", "text/plain; charset=utf-8")
    response_cookie("theme", "dark")
    print("created")
}
```

`redirect(url)` sends a redirect response. Bearer checks status codes and header names before it uses them.

## Components and named handlers

`COMPONENT` renders the default component handler. Use a colon to declare a named handler:

```capy
function COMPONENT:CARD(request : request) {
    var context := request_context(request)
    var title := dval_string(context["props"]["title"])
    print(<><article><h2><?= title ?></h2></article></>)
}
```

A handler can omit the request parameter when it uses only zero-argument request functions. Use the parameter to read component properties or task input.

## Sessions and CSRF protection

Call `session_start(name)` before you use a named session. Use `session_set`, `session_remove`, and `session_destroy` to change it.

Use `csrf_token`, `csrf_valid`, and `csrf_rotate` to protect forms. The API reference lists their overloads and default values.

## Custom HTTP servers

A `SERVE_HTTP` handler reads the request with the same request functions and writes the response with `print`, status, and header functions. `server_start_http` selects the default or named handler. The server remains host-owned; the Capy handler still runs in a fresh Bearer request workspace.

## WebSockets

A `WS` handler reads the current message with `ws_message()`. It can call `ws_send`, `ws_send_to`, or `ws_close`. The related `ws_*` functions provide connection IDs, scopes, binary state, and operation codes. Send and close operations return `bool`.
